# Beads feature extraction

Reviewed 13 November 2026. Source is [Beads](https://github.com/gastownhall/beads) commit [`d76ade2`](https://github.com/gastownhall/beads/commit/d76ade282c194aea66931a2da3d7e7eb586da3d5). This is a static review of documentation and selected implementation paths. Runtime behavior and performance were not tested. Source links below are pinned to this commit.

Beads provides persistent task context, a dependency graph, and coordination for coding agents. The central loop is create work, discover ready issues, claim, record progress, and close. The checkout also contains workflow templates, project memory, database history, replication, integrations, and operational tooling. Its README describes Dolt as the storage backend and explicitly documents Git-free usage. Git independence is already available in Beads. Beadcrumbs adds a different deployment constraint through a standard-library Python file and a plain JSON store. [README](https://github.com/gastownhall/beads/blob/d76ade282c194aea66931a2da3d7e7eb586da3d5/README.md)

## Traced coordination path

The inspected `readyClaimer.ClaimNext` validates the request, builds the same ready filter used for reads, and calls `ExecuteClaimNext` inside the database transaction wrapper. The operation selects and claims work, then hydrates relationships and counts. Hydration errors propagate so an incomplete result fails the transaction. The adapter resets its selected issue on retry and performs claim verification after the write. An empty ready set produces a nil claim and no changed tables. These are implementation observations for the selected path, with broader routing and backend behavior outside this review. [Adapter](https://github.com/gastownhall/beads/blob/d76ade282c194aea66931a2da3d7e7eb586da3d5/internal/storage/dolt/ready_claimer.go), [operation](https://github.com/gastownhall/beads/blob/d76ade282c194aea66931a2da3d7e7eb586da3d5/internal/storage/issueops/claim_next.go)

For Beadcrumbs, the corresponding sequence is acquire the store lock, validate the store, compute eligibility, select an issue, build its next record, atomically replace the issue file, and return that record. A combined claim-next command can reuse this sequence later. A ready listing by itself cannot reserve work.

## Lessons for the existing draft

The present Beadcrumbs draft already covers IDs, blocking dependencies, explicit claims, progress notes, revisions, and atomic publication. Its strongest simplification is that each command changes one authoritative record. Keeping notes in the issue makes a single-record commit possible.

The largest functional omissions are a detailed task brief, completion criteria, general listing, and explanations of blockers. Priority is useful for choosing work, but would change ready ordering. Mutable dependencies and reopening would invalidate the current assumption that claimed and closed issues always have closed dependencies. They need explicit policy before implementation.

Beads' guarded updates and claim verification also highlight ambiguity after interrupted writes. Beadcrumbs already documents that a failed response can follow a committed mutation. A later retry design should cover duplicate create and note requests, and a claim that succeeded before its token reached the worker.

## Review limits

The inventory covers the core workflow and selected advanced surfaces. It is not a complete command-by-command audit. Source code was inspected for ready selection and claim execution. Other features are described from the checked-out documentation and are identified as such in their evidence links. No Beads executable, migration, setup command, or external integration was run. The checkout was clean at the start of review.

The [proposed feature set](../features.md) translates these findings into Beadcrumbs scope and acceptance criteria.
